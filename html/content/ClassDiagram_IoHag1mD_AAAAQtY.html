Parameterized views

With an ordinary database view, one needs to expose the fields against which one might need to filter. For example, consider a view named xview that has the following fields: f1, f2, f3, f4

A developer might create a query such as: 

  select f1, f2, f3 from xview where f4=123

But exposing f4 might lead to unintended uses. For example, a developer might be tempted to join on the f4 field to another view or table. That can have some undireable consequences:

    Complex SQL finds its way into the application level, instead of being encapsulated at database level.
    Optimising query performance becomes difficult for DBAs (when the code is not readily available to DBA to embedd query hints)

A better solution would be to be able to execute a query such as: 

  select f1, f2, f3 from xview_pv(123)

Where xview_pv would be a parameterized view.

But, Oracle does not offer native parameterized views.

Parameterized views

The code shown in this document, generated by the extension, offers a practical implementation of a parameterized view. 

    select
          *
    from
          xxpv.xview(
            xxpvpub.xviewRefC(123)
          )

The xview() function, in the above example, is an implementation of a parameterized view. They allow parameters to operate on parts of the underlying SQL without having to expose those columns.
